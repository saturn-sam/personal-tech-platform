# GitOps Promotion Governance for a Shared Kubernetes Platform

## Context

The shared Kubernetes platform needed a consistent release decision process. Application teams were deploying through GitOps, but the promotion criteria between environments were still interpreted differently by platform operators, delivery teams, and approvers.

## Requirements

- Keep promotion checks consistent across staging and production.
- Preserve delivery-team autonomy for routine releases.
- Leave a clear audit trail for approval and rollback decisions.

## Constraints

- The workflow had to work with the existing GitLab CI/CD and GitOps repositories.
- Approval steps could not rely on informal chat history.
- Operators needed a review pattern that was fast enough for repeated use.

## Alternatives Considered

- Continue with team-specific promotion checklists stored in separate repositories.
- Require platform engineers to perform every promotion manually.
- Add more automation first and postpone the governance model.

## Decision

The platform adopted a single promotion checklist and release-note pattern that every team follows before moving changes forward. The decision favored repeatable review over custom team workflows so release evidence stayed comparable across environments.

## Implementation

The governance model was documented directly in PTKP and linked to the platform project. Promotion reviews now check manifest diffs, required approvals, expected observability impact, and rollback readiness before a change advances. The checklist is intentionally compact so it remains usable during normal operations rather than only during formal audits.

<Callout type="important" title="Why the operating model mattered">
  The issue was not a lack of deployment tooling. The issue was inconsistent decision-making around
  when a change was ready to move forward.
</Callout>

## Outcome

Promotion reviews became easier to audit, platform operators spent less time reconstructing release intent, and teams gained a documented path for proving that a deployment met the shared readiness bar.

## Lessons Learned

- Release governance should be written for routine use, not only for exceptional changes.
- Decision evidence is easier to maintain when it lives next to the technical guidance it supports.
- Lightweight checklists are more sustainable than approval workflows that depend on memory.

## Future Improvements

- Link deployment evidence from CI pipelines directly into the promotion record.
- Add a short retrospective template for failed promotions so lessons are captured consistently.
- Expand the pattern for multi-cluster promotion windows and maintenance freezes.
