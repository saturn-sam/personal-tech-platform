# PTKP Content Style Guide

Version: 1.0

Status: Approved

---

# Purpose

Define the writing style, terminology, formatting, and presentation standards for every piece of content published within the Personal Technical Knowledge Platform (PTKP).

This document ensures consistency regardless of when or why content is created.

---

# Writing Philosophy

PTKP is a technical knowledge platform.

Write as an experienced infrastructure engineer documenting solutions for other engineers.

Every document should educate.

Every document should be practical.

Every document should remain valuable years after publication.

---

# Tone

Content must be:

- Professional
- Technical
- Objective
- Precise
- Clear
- Concise

Avoid:

- Marketing language
- Buzzwords
- Clickbait
- Exaggeration
- Personal promotion

---

# Voice

Write in an instructional style.

Prefer:

- Explain
- Demonstrate
- Compare
- Validate

Avoid:

- Selling
- Persuading
- Self-promotion

---

# Technical Accuracy

Never publish assumptions as facts.

If something is version dependent:

- State the version.
- State any prerequisites.
- State limitations.

---

# Terminology

Use official vendor terminology whenever possible.

Examples:

- VMware Cloud Foundation
- vSphere Kubernetes Service
- OpenShift Virtualization
- Kubernetes
- GitLab CI/CD
- Terraform
- Ansible

Avoid unofficial abbreviations.

---

# Headings

Use only one H1.

Maintain logical heading hierarchy.

Prefer short descriptive headings.

---

# Paragraphs

Keep paragraphs focused.

One topic per paragraph.

Avoid unnecessarily long paragraphs.

---

# Lists

Use lists for:

- Requirements
- Procedures
- Comparisons
- Best practices
- Validation steps

Avoid excessive nesting.

---

# Code Examples

Every code block must:

- Specify language
- Be tested where practical
- Be production-oriented

Explain why the code exists.

---

# Commands

Shell commands should:

- Be copy-and-paste ready
- Include prerequisites where necessary
- Explain destructive operations

---

# Diagrams

Prefer Mermaid.

Architecture diagrams should remain simple.

Avoid decorative diagrams.

---

# Tables

Use tables when comparing:

- Technologies
- Versions
- Architectures
- Features

Avoid large tables that reduce readability.

---

# Images

Images must:

- Improve understanding
- Have descriptive alt text
- Be optimized

Avoid screenshots unless necessary.

---

# Links

Prefer official documentation.

Avoid unnecessary external references.

Use internal links whenever appropriate.

---

# Examples

Provide realistic enterprise examples.

Avoid artificial or trivial demonstrations.

---

# Metadata

Every document should include complete metadata as defined by the Content Model.

---

# Review Checklist

Before publishing verify:

- Technical accuracy
- Consistent terminology
- Grammar
- Formatting
- Metadata
- Internal links
- External references
- Accessibility
- Markdown validation
