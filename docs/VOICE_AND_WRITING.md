# Voice and Writing Guide

Version: 1.0

Status: Active

---

# Purpose

This document defines the editorial standards for the Personal Technical Knowledge Platform (PTKP).

Its purpose is to ensure every Knowledge Asset maintains a consistent voice, writing style, terminology, and documentation quality regardless of when it is written.

This document applies to all Articles, Architecture Guides, Lab Notes, Projects, Learning Paths, Case Studies, Technology Pages, and Documentation.

---

# Editorial Philosophy

PTKP exists to educate engineers through practical, experience-based documentation.

Every document should prioritize:

- Technical accuracy
- Clarity
- Practical value
- Long-term usefulness
- Professionalism

Readers should finish a document with a better understanding of the topic than when they started.

---

# Tone of Voice

The writing style should be:

- Professional
- Calm
- Precise
- Direct
- Respectful
- Educational
- Evidence-based

Avoid emotional or exaggerated language.

Do not attempt to impress the reader.

Allow the quality of the content to demonstrate expertise.

---

# Writing Principles

## Clarity

Prefer simple language over complicated language.

A clear explanation is better than a clever explanation.

---

## Precision

Use technically correct terminology.

Do not oversimplify concepts in ways that introduce inaccuracies.

---

## Practicality

Documentation should help readers solve real problems.

Theory should support implementation rather than replace it.

---

## Honesty

If limitations exist, document them.

If trade-offs exist, explain them.

If assumptions are made, state them explicitly.

---

## Neutrality

Present alternatives fairly.

Explain why a particular approach was chosen without dismissing other valid approaches.

---

# Audience

Assume the reader:

- Understands basic computing concepts.
- Is technically curious.
- Wants practical guidance.
- Appreciates well-structured documentation.

Do not assume expert-level knowledge of every technology.

Provide sufficient background when introducing advanced concepts.

---

# Document Structure

Long-form documentation should follow this general structure where appropriate:

1. Overview
2. Objectives
3. Background
4. Prerequisites
5. Architecture or Design
6. Implementation
7. Validation
8. Troubleshooting
9. Best Practices
10. Lessons Learned
11. References
12. Related Knowledge Assets

Not every section is required, but the flow should remain logical and consistent.

---

# Article Guidelines

Articles should focus on evergreen technical topics.

Avoid publishing content that quickly becomes obsolete unless historical context is important.

Examples of suitable article topics:

- Kubernetes Networking
- OpenShift Virtualization
- VMware Cloud Foundation
- Infrastructure Automation
- Terraform Patterns
- Enterprise Monitoring

---

# Lab Note Guidelines

Lab Notes are quick references.

They should:

- Solve one problem.
- Remain concise.
- Include commands where appropriate.
- Avoid unnecessary explanation.

Target reading time:

1–3 minutes.

---

# Architecture Guide Guidelines

Architecture Guides should explain complete solutions.

Each guide should include:

- Problem
- Requirements
- Constraints
- Assumptions
- Architecture Diagram
- Components
- Security
- Networking
- Storage
- Operations
- Backup
- Disaster Recovery
- Trade-offs
- Lessons Learned

Architecture Guides are expected to evolve over time.

---

# Project Documentation

Projects should describe engineering work rather than personal achievement.

Focus on:

- Business context
- Technical challenges
- Decisions
- Implementation
- Outcomes
- Lessons learned

Avoid résumé-style descriptions.

---

# Case Studies

Case Studies should explain why engineering decisions were made.

Include:

- Context
- Constraints
- Alternatives considered
- Decision
- Implementation
- Outcome
- Future improvements

---

# Learning Paths

Learning Paths should:

- Build knowledge progressively.
- Reference existing Knowledge Assets.
- Avoid duplicating content.
- Recommend a logical reading order.

---

# Terminology

Use terminology consistently throughout PTKP.

Preferred terms:

Article

Architecture Guide

Lab Note

Learning Path

Knowledge Asset

Technology

Project

Case Study

Certification

Resource

Download

Avoid switching between multiple names for the same concept.

---

# Capitalization

Use Title Case for:

- Page titles
- Section titles
- Navigation items

Use sentence case for normal paragraphs.

Maintain consistent capitalization for technology names.

Examples:

Kubernetes

OpenShift

VMware Cloud Foundation

GitHub

Cloudflare Pages

Terraform

Ansible

---

# Markdown Standards

Use:

- ATX headings (#)
- Fenced code blocks
- Tables where appropriate
- Relative links for internal references

Avoid inline HTML unless necessary.

---

# Code Examples

Every code example should:

- Specify the language.
- Include only relevant code.
- Be formatted consistently.
- Be tested before publication whenever practical.

Large code samples should be accompanied by an explanation.

---

# Command Examples

Commands should:

- Be copy-and-paste friendly.
- Include expected output where helpful.
- Explain potentially destructive operations.

---

# Diagrams

Use Mermaid whenever practical.

Diagrams should:

- Be readable.
- Focus on concepts.
- Avoid unnecessary detail.
- Use consistent naming.

---

# Images

Images should support understanding.

Avoid decorative screenshots.

Every image should include descriptive alt text.

---

# Tables

Tables should compare information clearly.

Avoid large tables that are difficult to read on mobile devices.

---

# Lists

Lists should remain concise.

Avoid unnecessary nesting.

---

# Links

Internal links should connect related Knowledge Assets.

External links should reference authoritative sources whenever possible.

Broken links should be corrected promptly.

---

# SEO Writing

Titles should be descriptive.

Descriptions should summarize the content accurately.

Avoid keyword stuffing.

Write for humans first.

Search engines second.

---

# Inclusive Language

Use respectful and inclusive language.

Avoid assumptions about the reader.

Avoid unnecessarily gendered language.

---

# Grammar

Use consistent spelling throughout the platform.

Choose one English variant and use it consistently.

Technical terminology should match official vendor documentation.

---

# Document Maintenance

Documentation is expected to evolve.

Update existing content whenever:

- Better practices emerge.
- Technology changes.
- Errors are discovered.
- Additional experience is gained.

Do not create duplicate documentation when an update is more appropriate.

---

# Final Principle

Write documentation that you would want to read five years from now.

Every document should remain technically valuable, well-structured, and maintainable long after its initial publication.
